# ISL · APP / WEB EVOLUTION LAYER · CURRENT
Fecha: 2026-09-23
Estado: ACTIVE DIRECTION · ADDITIVE · NON-DESTRUCTIVE · ISL ONLY

## PURPOSE
Redefine ISL app/web after the Upgrade without deleting the previous project surface.

The new app/web is NOT a reboot.
The previous version becomes an intentional submerged historical layer: ANCESTOR / LEGACY LAYER.

## MASTER DECISION
Do not start from zero.

Use:
RECOVER → CLASSIFY → PRESERVE → REDESIGN → RECONNECT → EXPOSE EVOLUTION.

The Upgrade becomes the current living surface.
The previous app/web becomes visible history, not dead code.

## MAKING-OF PRINCIPLE
Do not present evolution as:
"old bad → new good."

Present:
question → attempt → evidence → mutation → current state.

Preserve dignity of previous work.
Failed work becomes learning evidence.

## METHODOLOGY RULE
Every major app/web redesign should ask:
1. What is current authority?
2. What old function still works?
3. What is historical but valuable?
4. What must be hidden because it is operational/private?
5. What should be surfaced as evolution/making-of?
6. What can be removed from the current navigation without deleting history?

## AUTOMATION / BOT BEHAVIOR
Existing bots may:
- detect stale public surfaces;
- flag CURRENT vs deployed mismatch;
- surface major before/after milestones;
- prepare making-of candidates after meaningful decisions.

Bots may NOT:
- auto-publish legacy content;
- auto-promote old material to current;
- create new nav sections without human approval;
- expose private/security/supplier information.

## STOP RULE
Do not port a legacy feature because it existed.
Do not delete a legacy feature because it looks old.

Ask:
WHAT FUNCTION DID IT SERVE?
DO WE STILL NEED THAT FUNCTION?
WHERE DOES IT BELONG NOW?

## CURRENT RECOMMENDATION
Continue from the existing system architecture, but rebuild the visible app/web shell with stricter hierarchy.

This is a controlled renovation, not a greenfield reboot.
